# ARES-X Phase 1 Core Foundation: Five-service monorepo scaffold

A greenfield build of a cyber battlefield platform comprising a Go API Gateway (JWT, RBAC, 20+ endpoints), a Rust graph engine (Dijkstra, BFS, betweenness centrality, attack path discovery), a Go asset service (CRUD, ingestion, scoring), a Python attack-path engine (Monte Carlo simulation, MITRE ATT&CK mapping, CVE scoring), and a Next.js 14 frontend with military-themed dark UI. All services use in-memory storage with the intention of adding persistence later. The architecture is well-structured: clean separation of concerns, consistent error-response contracts, and deployment configs for both Docker Compose and Kubernetes.

**Watch for:** Hardcoded demo credentials with plaintext passwords in the API gateway (confirmed). The proto definitions and the Rust gRPC layer are structurally disconnected -- proto messages use `ares.common.UUID` wrappers while the Rust code uses hand-rolled structs that flatten to plain strings (confirmed). The frontend login page bypasses the actual auth API entirely, using `setTimeout` to simulate authentication (confirmed). The attack-path engine stores computed paths in a module-global list that grows unboundedly and is not thread-safe under concurrent requests (confirmed).

## High-level view

The API gateway implements a hand-rolled JWT library (HMAC-SHA256) and a hierarchical RBAC model that gates write endpoints behind role checks. The auth handler authenticates against a hardcoded demo user map with plaintext passwords, and the refresh token endpoint is gated behind auth middleware -- meaning a client cannot refresh once the access token expires.

The Rust graph engine is the most algorithmically dense service. Dijkstra, all-paths DFS, blast radius (BFS), betweenness centrality approximation, and cycle-detecting dependency analysis are implemented from scratch using only `std` collections. The gRPC interface layer is a mock: proto message types are hand-rolled Rust structs that diverge from the `.proto` definitions in pagination model, ID wrapping, and response structure.

The Python attack-path engine combines path-finding DFS, MITRE ATT&CK mapping (20 techniques), CVE-to-probability conversion, and Monte Carlo simulation. Paths are stored in a module-level mutable list that grows unboundedly, creating memory pressure and potential race conditions under FastAPI's async concurrency.

The Go asset service provides a clean in-memory CRUD repository behind a well-defined interface, with an ingestion pipeline (validate, normalize, deduplicate) and a weighted criticality scoring model. Deduplication uses linear scans that will become O(n^2) under bulk loads.

The frontend delivers a consistent military/tactical dark theme with SVG-based graph visualization, but is entirely disconnected from the backend: the login page uses `setTimeout` instead of calling the auth API, and all data pages render hardcoded mock data.

## Authentication posture and credential handling

The gateway authenticates via a hardcoded `demoUsers` map with plaintext passwords like `"admin-secret-2024"` compiled into the binary. The refresh token endpoint is guarded by the same `authMiddleware` that requires a valid, non-expired access token:

```go
// router.go - refresh requires auth, which requires non-expired access token
mux.Handle("POST /api/v1/auth/refresh", authMiddleware(http.HandlerFunc(authHandler.RefreshToken)))
```

Once the access token expires, the client has no way to use its refresh token -- it must re-authenticate with credentials. This defeats the entire refresh flow.

The MFA implementation accepts any 6-character string without validating against the generated TOTP secret. The secret is generated via `crypto/rand` and returned to the client during setup, but never stored server-side for subsequent verification. MFA is decorative.

The default JWT secret in config is `"ares-x-default-secret-change-in-production"`. The Docker Compose overrides it to `"change-me-in-production"`. Neither environment generates a random secret on startup or fails-closed when no secret is configured.

## Proto-to-implementation structural gap

The `shared/proto/graph.proto` defines messages using `ares.common.UUID` wrapper types, `PaginationRequest` messages with `page`/`page_size` fields, and a `QueryNodesResponse` that embeds a `Pagination` message. The Rust implementation defines its own `proto` module with plain structs using `page_token: String` (cursor-based) rather than `page: i32` (offset-based), and carries `next_page_token`/`total_count` directly on the response rather than nested inside `Pagination`.

Concrete failures this causes:
- A proto-generated client sends `PaginationRequest { page: 2, page_size: 20 }` but the Rust server expects `page_token: "20"` and `page_size: 20`.
- The proto `Node.id` is `ares.common.UUID { value: string }` (a nested message), but the Rust `ProtoNode.id` is just `String`.
- No `.proto` file is actually compiled in the Rust build -- the `build.rs` references proto compilation but runtime types are hand-rolled.

This will fail at the wire-protocol level when any service tries to communicate via actual protobuf serialization.

## Rust graph algorithms: edge cases

If `edge.weight` is exactly `0.0`, Dijkstra assigns `f64::MAX / 2.0` as cost. Two such zero-weight edges in sequence would sum to `f64::MAX`, which compares correctly but path reconstruction reports a misleadingly large cost. Worth guarding against or documenting the "weight must be > 0" invariant.

The betweenness centrality sampling uses a deterministic stride through the node-pair space, but `HashMap::keys()` order is randomized per process in Rust. Results will differ between runs even on the same graph. If reproducibility matters for auditing, the node list should be sorted before sampling.

## Attack-path engine concurrency and state management

```python
_computed_paths: list[AttackPath] = []
```

FastAPI runs on an async event loop. `list.extend()` (used in the compute endpoint) is not atomic at the application level -- a concurrent request could read a partially-extended list. This list grows without bound: every compute request appends paths that are never pruned, and the simulation endpoint searches the entire list linearly by ID.

The convergence detection in Monte Carlo (stop early if std_dev of last 1000 samples < 0.001) is a sound optimization, but the threshold is hardcoded with no way to tune it per-path.

## Frontend-backend integration gap

The login page does not call the API:

```tsx
setTimeout(() => {
  setShowMfa(true);
  setIsLoading(false);
}, 800);
```

`frontend/src/lib/auth.ts` contains a complete `login()` function that calls `api.post('/api/v1/auth/login', ...)` and stores tokens in localStorage -- but it's never imported by the login page. The hooks (`useAuth.ts`, `useAssets.ts`, `useGraph.ts`) exist but are not wired into any page component. All pages render hardcoded mock data regardless of backend state.

## Docker Compose environment variable mismatch

The API gateway's `config.go` reads these env vars:

| Config reads | Docker Compose sets |
|---|---|
| `DATABASE_URL` | `POSTGRES_DSN` |
| `REDIS_URL` | `REDIS_ADDR` |
| `GRAPH_ENGINE_URL` | `GRAPH_ENGINE_ADDR` |
| `ASSET_SERVICE_URL` | `ASSET_SERVICE_ADDR` |
| `ATTACK_PATH_ENGINE_URL` | `ATTACK_PATH_ENGINE_ADDR` |

The gateway will silently fall back to localhost defaults that won't resolve inside the Docker network. The service will start but fail on any cross-service or database operation.

## Kubernetes secrets in version control

```yaml
JWT_SECRET: Y2hhbmdlLW1lLWluLXByb2R1Y3Rpb24=  # "change-me-in-production"
POSTGRES_PASSWORD: Y2hhbmdlLW1lLWluLXByb2R1Y3Rpb24=
```

Base64 is encoding, not encryption. For a security platform, secrets should be managed via external secret management (Vault, sealed-secrets) and the YAML should contain references, not values.

## Asset service deduplication scaling

The ingestion pipeline's `FindDuplicate()` iterates all assets on every insert -- O(n) per insert, O(n^2) for bulk operations. The `RecalculateAll()` scoring method iterates all assets and writes scores without preventing concurrent reads of stale data. Both are acceptable for in-memory Phase 1 but will need index-based lookups and transactional scoring when persistence is added.
